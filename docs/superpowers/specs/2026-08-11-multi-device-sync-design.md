# 多端数据同步设计（2026-08-11）

- 状态：已获用户口头批准（2026-08-11：LeanCloud 国内版开发版 + 本地为主架构 + 全量数据同步）

## 1. 背景与目标

产品当前为纯本地单机（FastAPI + SQLite + 原生前端）。目标：同一账号在电脑（EXE/网页）与手机（APK）间数据同步更新，同时**保持完全离线可用**的产品特性。

## 2. 总体架构

- 本地 SQLite 为**真源**：所有业务读写不变，操作即时生效，断网完全可用。
- LeanCloud 国内版（开发版）为**云端同步副本**：每天 3 万次 API + 1GB 存储免费额度。
- 新增同步引擎模块（Python 后端内）：后台静默做增量双向同步，不改变现有业务读写路径。

## 3. 账号体系

- LeanCloud 用户系统（AVUser）成为账号唯一源；本地 `User` 表降级为离线缓存。
- 注册/登录需联网一次（走 LeanCloud），成功后凭据缓存本地，之后断网可登录使用。
- 现有本地账号一次性迁移：用原用户名+密码在 LeanCloud 注册绑定，数据自动挂到新账号。
- 忘记密码的安全问题重置：答案哈希存入 LeanCloud 用户自定义字段，逻辑不变。

## 4. 数据表改造（阶段 2 地基）

- 所有业务表主键改为 **UUID 字符串**（避免多端自增 ID 撞车），外键同步更换。
- 同步表统一加 `updated_at`（时间戳）与 `deleted`（软删除墓碑，0/1）。
- 打卡连续天数（streak）为派生字段：按 `last_checkin` 在本地重算，不同步字段本身。

## 5. 同步引擎（阶段 4）

- 增量同步：只传 `updated_at > 上次同步点` 的记录，双向。
- 触发时机：应用启动时、专注结束时、每 5 分钟静默检查、设置页"立即同步"按钮。
- 离线改动进现有离线队列（`flushQueue` 机制复用），联网后自动补推。
- 冲突策略：**后写覆盖**（比 `updated_at`，谁新谁赢）；删除走软删除墓碑，避免"删了又回来"。

## 6. 设置入表

- 将散在浏览器 `localStorage` 的设置键（主题、提醒开关、黑名单等）迁入 `Setting` 表，随账号同步。

## 7. 实施阶段

- **阶段 1**：数据导出/导入（JSON 全量）——备份与数据搬家兜底，EXE/手机版数据互通地基。
- **阶段 2**：表地基改造（UUID + `updated_at` + `deleted`）+ 设置入表。
- **阶段 3**：LeanCloud 账号接入（注册/登录/密码重置 + 本地离线缓存）。
- **阶段 4**：同步引擎（增量双向同步 + 冲突处理 + 离线队列 + 同步状态 UI）。
- **阶段 5**：手机版（复用同步引擎，纯记录功能：香计时/打卡/日记，无进程检测）。

## 8. 不做的事（YAGNI）

- 不做多端实时冲突合并（如日记段落级合并）——后写覆盖对个人数据足够。
- 阶段 1 不导出头像文件（LeanCloud 文件存储在阶段 3/4 处理）。
- 不做云端实时推送（WebSocket）——启动/定时/触发式增量拉取足够。
